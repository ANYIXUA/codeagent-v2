# 002 数据库持久化规格

上位规格见 `../../AGENT.md`，提交和查询契约见 `../001-run-api/spec.md`。

## 目标

用户退出 CLI 后，再连接同一个数据库启动 CLI，仍可用原来的 `run_id` 查到该次运行的结果或失败原因。

## 本阶段范围

使用 PostgreSQL 16 保存运行记录与创建事件，提供从空数据库初始化和后续升级数据库结构的流程。CLI 调用 RunAPI 提交运行，并查询结果、事件与执行轨迹。固定执行器同步完成运行，终端以文本显示结果。

## CLI 契约

| 命令 | 终端行为 |
|---|---|
| `/run <请求>` | 校验输入，等待执行结束并确认运行记录与 `run.created` 事件均已提交，再显示 `run_id`、状态和结果或失败原因 |
| `/get <run_id>` | 在当前组织内读取该次运行。成功查询且无记录时提示「找不到这次运行」 |
| `/events <run_id>` | 展示当前组织内该次运行的事件，按 `sequence` 升序排列 |
| `/trace <run_id>` | 展示当前组织内该次运行的记录、步骤、事件、模型调用、工具调用和检查点。没有记录的区块显示为空 |

## 数据要求

- 每条记录以 `run_id` 唯一标识，保存 `run_type`、完整 `input`、`status`、`output` 或 `error`，以及 `created_at`、`started_at`、`ended_at`。
- 时间戳使用 UTC。查询应返回提交时的记录内容和时间戳。固定执行器返回失败时，同样保存记录并返回 `run_id`。
- 初始化和升级使用带版本的迁移流程。重复应用同一版本后，已有记录仍可查询，记录内容一致。
- 创建运行与写入其 `run.created` 事件在同一事务中提交，写入失败时一并回滚。事件的 `sequence` 在各自的运行内从 1 开始严格递增。

## 默认约定

- 本地 CLI 从 `CODEAGENT_ORG_ID` 和 `CODEAGENT_USER_ID` 读取身份，缺省时分别使用稳定的 `local-org` 和 `local-user`。同一数据库中的运行记录按实际生效的 `org_id` 和 `user_id` 保存。
- 同一组织重复提交相同的 `idempotency_key` 时返回明确的冲突错误，保留已有运行和事件，不覆盖原记录。只有 `agent_runs.id` 主键冲突才重新生成 `run_id` 并重试写入；固定执行器只执行一次。
- 持久化继续使用 JSONB。持久化入口在执行前校验实际的 U+0000 字符，覆盖嵌套 JSON 的键和值。普通文本中的反斜杠加 `u0000`（六个字符）仍可正常保存和读回。

## 失败行为

- 非法输入在执行前提示原因，运行记录数不变。实际的 U+0000 字符按非法输入处理。
- 初始化和升级失败时，迁移命令以非零退出码结束。CLI 启动时若连不上数据库或数据库版本未就绪，提示原因并以非零退出码结束。
- 写入未获数据库确认时，提示保存未确认。读取失败时，提示查询失败。CLI 继续接收命令。
- 同一组织重复使用 `idempotency_key` 时提示冲突原因，已有运行、结果和事件保持不变。

## 验收条件

| 编号 | 场景 | 预期结果 |
|---|---|---|
| AC-01 | 使用空的 PostgreSQL 16 数据库，按文档初始化并启动 CLI | 使用 `/run 解释任务队列` 可创建一条成功记录 |
| AC-02 | 记录 AC-01 的 `run_id`，退出并重启 CLI，连接同一个数据库执行 `/get <run_id>` | 显示同一个 ID、执行成功和原结果。RunAPI 读回的输入、状态、结果和三个时间戳与提交返回一致 |
| AC-03 | 提交 `/run [fail] 数据库验收`，退出并重启后按 ID 查询 | 提交返回 `run_id`。重启后可查到执行失败和原失败原因，失败记录的输入和时间戳一致 |
| AC-04 | 提交空请求和超过 2000 字符的请求，再查询未知 ID | 两次提交均提示输入错误，记录数不变。查询提示「找不到这次运行」 |
| AC-05 | 在已有成功和失败记录的数据库上再次执行迁移 | 迁移正常结束，两条记录均可按原 ID 查询，字段值一致 |
| AC-06 | 分别尝试在数据库不可用时运行迁移、在数据库不可用或版本未就绪时启动 CLI、在 CLI 运行中读写不可用的数据库 | 迁移和启动失败时提示原因并以非零退出码结束。运行中按操作提示保存未确认或查询失败，可继续输入 `/help` 或 `/exit` |
| AC-07 | 用第一章的 `/run` 和 `/get` 检查 SQLAlchemy 持久化 | CLI 通过 PostgreSQL 存取运行记录，跨进程查询结果一致 |
| AC-08 | 核对连接与数据访问边界 | `database.py` 管理引擎与会话，`repository.py` 集中执行 SQLAlchemy 查询和写入，CLI 经 RunAPI 调用存储层 |
| AC-09 | 为一次运行追加事件后执行 `/events <run_id>` | 首条为 `run.created`，所有事件按 `sequence` 升序输出。同一运行内追加事件的序号严格递增 |
| AC-10 | 为一次运行预置步骤、事件、模型调用、工具调用和检查点，再执行 `/trace <run_id>` | 返回运行及各类关联记录，关联区块与输入的运行 ID 一致 |
| AC-11 | 在另一组织的上下文查询已存在的运行 ID | `/get`、`/events` 和 `/trace` 都提示「找不到这次运行」，各查询均按 `org_id` 限定 |
| AC-12 | 分别正常创建运行、让 `run.created` 写入失败 | 正常提交时从另一连接可同时查到运行和序号为 1 的 `run.created`。事件写入失败时，数据库中没有这次运行或对应事件 |
| AC-13 | 不设置身份环境变量启动 CLI，再用 `CODEAGENT_ORG_ID` 和 `CODEAGENT_USER_ID` 覆盖后提交 | 未设置时数据库行使用 `local-org` 和 `local-user`；设置后使用指定的 `org_id` 和 `user_id` |
| AC-14 | 同一组织用相同 `idempotency_key` 提交两次，并分别制造运行主键冲突 | 第二次提交返回冲突错误，原运行和事件保留。主键冲突时生成新 `run_id` 并成功写入，固定执行器只执行一次 |
| AC-15 | 提交嵌套 JSON 键或值中含实际 U+0000 的请求，再提交含普通文本 `\u0000` 的请求 | 前者在执行前被拒绝且不新增运行记录；后者正常保存并原样读回 |
